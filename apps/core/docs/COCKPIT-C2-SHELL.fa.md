# مشخصات مرحله C2 — پوسته Cockpit

## وضعیت و هدف

- مرحله: C2
- وضعیت: مشخصات طراحی پیش از پیاده‌سازی نهایی
- مرجع بالادستی: `COCKPIT-DASHBOARD-SPEC.fa.md`
- تمرکز: ساختار فضایی، تراکم اطلاعات و رفتار مرور جزئیات

هدف C2 تعریف پوسته‌ای است که مدیر بتواند در چند ثانیه مهم‌ترین مسئله را ببیند، اثر آن را بفهمد و با یک تعامل به جزئیات اولیه برسد.

## ساختار Desktop

### Top System Bar

- ارتفاع پایه: `48px`
- اطلاعات هویتی، وضعیت محیط و کنترل‌های سطح سیستم در این نوار قرار می‌گیرند.
- Top System Bar نباید با Attention Queue رقابت بصری داشته باشد.

### Main Cockpit

ساختار اصلی سه‌ناحیه‌ای است:

1. **Workforce Left Rail**
2. **Command Center**
3. **Production Right Rail**

ابعاد اولیه، فرضیه طراحی هستند و پس از بررسی Wireframe قابل تنظیم‌اند؛ نقش و ترتیب ستون‌ها ثابت است.

| Viewport | Workforce / Left | Command / Center | Production / Right | فاصله ستون‌ها | حاشیه بیرونی |
| --- | ---: | --- | ---: | ---: | ---: |
| حدود `1920px` | حدود `320px` | Flexible و غالب | حدود `392px` | `12px` | حدود `16px` |
| حدود `1440px` | حدود `256px` | Flexible و غالب | حدود `320px` | `12px` | حدود `16px` |

## Center / Command Core

ناحیه مرکزی سه لایه دارد:

1. Status Summary
2. Attention Queue
3. Upcoming Commitments

در نسخه اول، Attention و Decision یک جریان مشترک هستند. مدیر نباید برای تشخیص «چه چیزی مهم است» بین دو صف مستقل جابه‌جا شود.

### ظرفیت Attention

- در حالت معمول حدود ۵ تا ۷ مورد مهم نمایش داده شود.
- در ارتفاع کمتر، تعداد ردیف‌ها کاهش یابد؛ فونت کوچک نشود.
- موارد کم‌اهمیت‌تر به ادامه صف یا جزئیات منتقل شوند.

### ترتیب Attention

ترتیب ارزیابی و نمایش:

**فوریت → زمان باقی‌مانده → دامنه اثر → مدت انتظار**

شدت فنی به‌تنهایی معیار اولویت بالا نیست.

### محتوای هر Attention

هر ردیف باید حداقل شامل این اطلاعات باشد:

- مسئله
- اثر احتمالی
- زمان یا Deadline
- ماژول مالک
- تازگی و اعتبار داده
- مسیر بررسی

## Workforce Left Rail

این Rail باید به سؤال زیر پاسخ دهد:

> چه کسی روی چه کاری است و کجا ظرفیت یا تعارض داریم؟

نمایش باید فشرده و عملیاتی باشد و شامل این مفاهیم شود:

- Coverage
- Capacity
- Conflict
- Important Workforce Attention

در ارتفاع مناسب، حدود ۵ تا ۷ ردیف نمایش داده می‌شود. حقیقت داده و جزئیات عملیاتی همچنان متعلق به Workforce است.

## Production Right Rail

این Rail باید در آینده به سؤال زیر پاسخ دهد:

> تولید کجا ایستاده و چه چیزی مانع ادامه است؟

Production در C2 همچنان Mock / Experimental است. موارد زیر فقط برای نمایش معماری UI استفاده می‌شوند:

- Important WorkOrders
- Progress
- Deadline
- Blocking Material
- Bottleneck

هیچ‌یک از این موارد، منطق نهایی کسب‌وکاری Production نیستند. در C2 نباید Threshold، اولویت، تعریف ریسک یا رفتار قطعی جدیدی برای Production اختراع شود.

## Important Changes

Important Changes بین Main Cockpit و Vital Strip قرار می‌گیرد.

- فقط ۲ تا ۳ تغییر مهم انسانی یا کسب‌وکاری نمایش داده شود.
- این بخش Log فنی، Event Stream خام یا تاریخچه همه تغییرات نیست.
- هر مورد باید به فهم تغییر معنادار در وضعیت کمک کند.

## Vital Strip

Vital Strip در لبه پایین Cockpit قرار می‌گیرد.

ارتفاع پایه:

- Desktop بزرگ: حدود `88px`
- Viewport فشرده: حدود `80px`

شش جایگاه اولیه:

1. Sales
2. Cash
3. Orders
4. Workforce
5. Production
6. Data

هر Vital شامل این اجزا است:

- مقدار
- Context کوتاه
- Trend، فقط در صورت معنی‌داربودن

Vitalها نباید به کارت‌های بزرگ و مستقل تبدیل شوند. Strip باید به شکل یک نوار پیوسته و سریع‌خوان عمل کند.

## Detail Drawer

جزئیات اولیه در یک Drawer غیرمودال از راست باز می‌شوند.

عرض پایه:

- Desktop بزرگ: حدود `480px`
- Viewport حدود `1440px`: حدود `420px`

قواعد Drawer:

- Layout اصلی را هل ندهد.
- Context Cockpit را حفظ کند.
- Top System Bar و Vital Strip را از بین نبرد.
- اسکرول داخلی داشته باشد.
- بستن Drawer کاربر را به همان مورد قبلی برگرداند.
- در V1 هیچ عملیات کسب‌وکاری اجرا نکند.

ساختار محتوا:

**مسئله → اثر → شواهد → گزینه‌ها → اقدام/مسیر → سابقه**

| Secondary Text | حدود `12–13px` |
| KPI | حدود `24–28px` |

## سلسله‌مراتب بصری

چهار سطح نمایش:

1. Critical
2. Attention
3. Operational
4. Context

رنگ شدید باید کمیاب باشد. قرمز یا کهربایی نباید کل پنل را پر کند.

شدت هر وضعیت با ترکیب سه نشانه نمایش داده می‌شود:

- رنگ
- کلمه
- نشانه یا Icon

هیچ وضعیت مهمی نباید فقط با رنگ منتقل شود.

## رفتار Mobile

C2 پوسته Desktop را تعریف می‌کند، اما Mobile نباید نسخه فشرده سه ستون باشد. در Mobile، همین اطلاعات باید به Commander Feed اولویت‌بندی‌شده تبدیل شوند. کاهش ارتفاع یا عرض نباید با کوچک‌کردن فونت عملیاتی جبران شود.

## پنج حالت Wireframe الزامی

پیش از پیاده‌سازی نهایی، این پنج حالت باید جداگانه بررسی شوند:

1. روز عادی
2. چند مشکل هم‌زمان
3. داده Stale / Partial / Error
4. Drawer باز
5. Viewport فشرده

## معیارهای UX

هدف آزمایشی ارزیابی:

- حدود ۵ ثانیه برای پیدا کردن مهم‌ترین مسئله
- حدود ۱۵ ثانیه برای فهم اثر و مالک یا مقصد بررسی
- یک Interaction برای رسیدن به جزئیات اولیه

این زمان‌ها معیار نهایی نیستند و باید با مدیر واقعی بررسی و اعتبارسنجی شوند.

## خارج از دامنه C2

- اجرای عملیات کسب‌وکاری از داخل Core
- اتصال واقعی Production یا Workforce
- API، دیتابیس یا Mahak adapter واقعی
- تعریف منطق نهایی WorkOrder، Bottleneck یا Blocking Material
- تغییر قرارداد مشترک
- تغییر P06 یا MAHAK-GATE

## قانون تغییر

Codex اجازه ندارد هنگام پیاده‌سازی، ساختار اصلی Cockpit را بدون ثبت تصمیم طراحی تغییر دهد.

اگر یک محدودیت فنی نیازمند تغییر در یکی از موارد زیر بود، ابتدا فقط باید گزارش داده شود:

- Spatial Layout
- نقش Core
- معماری Attention
- Data Trust
- مالکیت ماژول‌ها
- تعامل Drawer
