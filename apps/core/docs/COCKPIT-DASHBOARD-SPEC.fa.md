# مشخصات مرجع داشبورد Cockpit مستر جم

## وضعیت سند

- نقش سند: Master Specification برای جهت طراحی Cockpit در Core
- وضعیت: مرجع رسمی پیش از redesign
- دامنه: فقط تجربه مدیریتی `apps/core`
- سند مرحله اجرایی مرتبط: `COCKPIT-C2-SHELL.fa.md`

این سند جهت اصلی محصول و معماری اطلاعات Cockpit را تثبیت می‌کند. تغییر در ساختارهای اصلی تعریف‌شده در این سند، بدون ثبت تصمیم طراحی مجاز نیست.

## جمله مرجع

> مدیر باید مثل یک خلبان، با یک نگاه وضعیت مستر جم را بفهمد؛ فقط موارد مهم را ببیند، خطر را زود تشخیص دهد و بداند برای اقدام باید به کجا برود.

## تعریف محصول

Core یک وب‌سایت مدیریتی عمومی یا مجموعه‌ای از کارت‌های رایج SaaS نیست. صفحه اصلی Core یک «داشبورد خلبان / Cockpit Dashboard» است که باید مانند کابین کنترل، مهم‌ترین وضعیت‌ها و ریسک‌های مستر جم را در یک نمای منسجم نشان دهد.

مسیر اصلی تجربه مدیر:

**دیدن → فهمیدن → تصمیم گرفتن → رفتن به محل اقدام**

Core در وضعیت فعلی سه نقش دارد:

1. Observe — مشاهده وضعیت
2. Understand — فهم اثر و زمینه
3. Navigate — رفتن به محل درست بررسی یا اقدام

Core در این مرحله محل اجرای عملیات کسب‌وکاری نیست. نقش Execute در ماژول مالک باقی می‌ماند.

## اصول ثابت Cockpit

### تجربه اصلی

- Desktop تجربه اصلی Cockpit است.
- اطلاعات حیاتی باید تا حد ممکن در اولین Viewport قابل مشاهده باشند.
- نمایش باید Scan-friendly باشد؛ متن‌های طولانی نباید جای سیگنال‌های سریع و قابل تشخیص را بگیرند.
- تراکم اطلاعات باید فشرده اما خوانا باشد؛ هدف «Compact but not crowded» است.
- رنگ شدید باید کمیاب بماند و فقط برای ایجاد تمایز واقعی استفاده شود.

### معماری فضایی Desktop

- Workforce همیشه در Rail سمت چپ قرار می‌گیرد.
- Command / Attention همیشه ناحیه مرکزی و غالب است.
- Production همیشه در Rail سمت راست قرار می‌گیرد.
- Vital Signals همیشه در لبه پایین Cockpit قرار می‌گیرند.
- Attention مهم‌ترین ناحیه صفحه و نقطه شروع نگاه مدیر است.

این جایگاه‌ها بخشی از مدل ذهنی Cockpit هستند و صرفاً یک انتخاب تزئینی محسوب نمی‌شوند.

### سلامت کسب‌وکار و سلامت داده

Business Health و Data Health دو مفهوم مستقل‌اند:

- Business Health می‌گوید چه اتفاق مهمی در کسب‌وکار افتاده یا چه ریسکی نیازمند توجه است.
- Data Health می‌گوید داده چقدر تازه، کامل و قابل اعتماد است.

خرابی فنی یا شدت فنی به‌تنهایی نباید یک مورد را به بالاترین اولویت کسب‌وکاری تبدیل کند. در مقابل، داده سالم نیز به معنی نبود مسئله کسب‌وکاری نیست.

### Attention و مسیر اقدام

- صف Attention باید فقط موضوع‌هایی را نشان دهد که به تصمیم، ریسک یا فهم وضعیت کسب‌وکار کمک می‌کنند.
- مدیر باید بتواند مسئله، اثر، زمان، مالک و مقصد بررسی را سریع تشخیص دهد.
- جزئیات از طریق Drill-down، Drawer یا ورود به ماژول مالک باز می‌شوند.
- مشاهده جزئیات نباید Context اصلی Cockpit را از بین ببرد.
- در نسخه فعلی، هیچ عملیات کسب‌وکاری از داخل Cockpit اجرا نمی‌شود.

## رفتار داده

چهار حالت اصلی داده باید در تمام redesignها حفظ شوند:

- Healthy: داده معتبر و تازه است.
- Stale: آخرین داده معتبر وجود دارد اما قدیمی است.
- Partial: بخشی از داده یا بعضی قسمت‌های ماژول در دسترس نیست.
- Error: دریافت فعلی شکست خورده است اما UI از کار نمی‌افتد.

اگر Last Known Good وجود دارد، باید به‌وضوح از داده فعلی جدا و به‌عنوان مرجع تاریخی معرفی شود. خطای فنی خام نباید مستقیماً به مدیر نمایش داده شود.

## مالکیت ماژول‌ها

- Workforce مالک حقیقت برنامه هفتگی، کارکنان، ظرفیت و تعارض‌های مرتبط است.
- Production تا زمان تعریف منطق واقعی، فقط با داده Mock / Experimental نمایش داده می‌شود.
- نمایش آزمایشی Production نباید به‌عنوان منطق قطعی محصول یا داده عملیاتی واقعی برداشت شود.
- Core خلاصه مدیریتی را مشاهده و ترکیب می‌کند؛ حقیقت دامنه در ماژول مالک باقی می‌ماند.

## تجربه Mobile

Mobile نسخه کوچک‌شده Desktop نیست. تجربه Mobile باید به شکل **Commander Feed** طراحی شود:

- اولویت با مهم‌ترین مسئله و اقدام بعدی است.
- ترتیب محتوا جایگزین معماری هم‌زمان سه‌ستونه Desktop می‌شود.
- اطلاعات زمینه‌ای بعد از سیگنال‌های مهم قرار می‌گیرند.
- تراکم با حذف یا اولویت‌بندی کنترل می‌شود، نه با کوچک‌کردن افراطی فونت.

## مرزهای ثابت این مرحله

- هیچ اتصال واقعی، API، دیتابیس یا Mahak adapter فعال نمی‌شود.
- `apps/workforce` تغییر نمی‌کند.
- `packages/module-contracts` بدون تصمیم و بررسی هماهنگ تغییر نمی‌کند.
- وضعیت P06 و شرط MAHAK-GATE دست‌نخورده می‌ماند.
- Production همچنان Mock / Experimental است.

## قانون تغییر طراحی

Codex اجازه ندارد هنگام پیاده‌سازی، ساختار اصلی Cockpit را بدون ثبت تصمیم طراحی تغییر دهد.

اگر یک محدودیت فنی نیازمند تغییر در یکی از موارد زیر بود، ابتدا باید فقط گزارش و تصمیم جداگانه درخواست شود:

- Spatial Layout
- نقش Core
- معماری Attention
- Data Trust
- مالکیت ماژول‌ها
- تعامل Drawer
